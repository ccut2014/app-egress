# Monitor-only application rules

This is the current AppEgress feature documentation. AppEgress is the renamed TrafikRuler fork; pre-rename validation below refers to historical TrafikRuler binaries. See [UPSTREAM.md](../UPSTREAM.md).

In **Add rule**, choose a program, then **Monitor only**. No adapter is required. Expand **Connection details** on its card. Existing rules remain adapter-routing rules because the serialized `Rule.Mode` defaults to zero (`Route`); `Monitor` is one. The existing global Pause control also pauses monitoring.

## What is observed

- Read-only Windows IP Helper TCP/UDP owner-PID tables, sampled approximately once per second. Matching uses the existing full-path or executable-name rule semantics; it does not automatically include differently named child processes.
- TCP local/remote addresses and ports, PID and state, including LISTEN records. UDP tables provide only local bindings and PID, so a UDP entry never claims a remote address or an outgoing adapter.
- For a non-local TCP destination, a `GetBestRoute2` lookup using its local and remote IP addresses. This is the current Windows route query, **not evidence of the adapter that carried a particular packet**, nor a guarantee of VPN permission, NAT behavior, forwarding or reachability. Changes to routing, existing socket interface constraints, VPN interception, other AppEgress routing rules and other network compartments can make the actual path differ. Scoped IPv6/link-local routes are left unknown because the existing route wrapper cannot supply a scope ID.
- The current user's manual Windows proxy registry setting (`ProxyEnable` / `ProxyServer`) and whether `AutoConfigURL` is configured. Literal IP addresses and `localhost` are compared to TCP remote endpoints. Proxy hostnames are not resolved. WinHTTP settings, environment variables, application-specific settings and automatic discovery are not inspected. PAC is not fetched or executed. A matching endpoint is a **connection to a configured proxy endpoint**, not proof of the protocol in use or of successful upstream forwarding. Enabled proxy configuration alone never labels an application's connections as proxied.
- Local TCP peers are identified by the full reversed endpoint tuple and PID, with IPv4-mapped IPv6 normalization. A unique matching listener is a fallback labeled as a candidate, rather than a confirmed reverse connection. Ambiguous ownership remains unknown, including when a unique listener exists alongside conflicting reverse records.

## Network path evidence

Monitor cards now summarize their current route or proxy evidence even while collapsed. Expanded cards separate a network overview, the original connection endpoints, and selectable per-connection evidence details. Multiple kinds of evidence are shown as multiple paths, rather than choosing one VPN for the entire application. The displayed count is explicitly a **current snapshot**, not a connection history, command counter or traffic activity counter.

For a local connection, the application can show the peer PID and connection-table match, then the peer's other active TCP connections and their route queries. A peer query returning a VPN interface is labeled **local peer route evidence**, not an established forwarding path of the original application. Even one apparent upstream connection does not prove that it carries the original application's data. Arrows between processes denote a matched local connection, not payload correlation. Listener-only ownership is explicitly weaker.

Only one local peer is examined. Up to eight of its other active TCP connections are shown, with the total candidate count and a limit notice. The reverse of the observed connection is removed, and connections associated with the peer's known listening sockets are excluded as accepted connections. Direction inferred from a listener can be incomplete; remaining rows are still described as other connections. Cycles and deeper local chains are not recursively expanded. Different route queries are cached only within the same poll snapshot.

Connections to the configured system proxy endpoint are identified separately from related-process proxy connections. Related-process endpoint matches never turn the application's original connection into a confirmed proxy connection. A known local system proxy process's shared upstream connections are not analyzed as the application's upstream, including when the observed connection is to another port of that process (for example its management port). The proxy's selected node, multiplexed sessions, actual forwarding and quota consumption remain unknown. No endpoint match is labeled as proof of a proxy protocol or of proxy billing; absence of a match is limited to the displayed snapshot and does not rule out other proxies.

For non-local TCP rows, a source-address adapter match is displayed when the adapter inventory contains a unique matching selected address. This is not exhaustive because that inventory stores selected IPv4/global IPv6 addresses, not every address. Missing source ownership stays unknown. If the source-address interface and `GetBestRoute2` result disagree, the UI marks the actual path as needing confirmation. Neither result is substituted for verified packet transmission. Missing tables and display limits are called out in the evidence overview.

## Isolation and privacy

Monitor rules are excluded from `RoutingSnapshot`. Routing matching, filter construction, NAT revalidation and connection resetting also explicitly reject monitor rules. A fresh monitor rule does not start the WinDivert socket listener or packet capture. When the last routing rule is stopped, both existing WinDivert handles are closed. Adding a monitor alongside an existing routing rule does not override that rule.

Changing an existing routing rule to monitor mode stops its previous routing behavior: the usual cleanup of that old rule's NAT connections can cause reconnects. For observation without changing an existing routing rule, add a separate monitor rule.

Monitoring does not alter routes, adapter bindings, DNS settings, system proxies, firewall rules, VPN configuration, packets or connection state. It sends no test connections and performs no SSH or server actions. No payload is captured. Snapshot endpoints are held in memory and are not appended to the application log or settings. Existing ordinary rule logs still contain the selected program path. The UI/clipboard/screenshots and process memory can expose connection metadata; closing or pausing a rule clears its displayed snapshot, without claiming secure memory erasure.

Each snapshot displays at most 200 records and retains the total count. No history file is created. The first 200 TCP records have priority over UDP rows; totals still show all UDP bindings. Tables are not atomic with process enumeration: processes can exit, PIDs can be reused between reads, and short connections may be missed. Protected or unreadable processes can be absent. Native table errors are shown as incomplete data, not a successful empty sample. DNS delegated to a Windows service is not attributed to the original app. Byte totals and speeds are not sampled and are hidden for monitor-only cards.

The application's existing administrator launch requirement is unchanged. Monitoring itself only uses read-only OS APIs; it does not make routing mode safer or provide a kill switch. No external dependencies are added.

## Validation status for this change

The AppEgress rename, namespace/project moves, legacy-settings fallback and startup-path compatibility have not been built or tested. No AppEgress executable or release has been produced or launched during the rename. The observations below happened before renaming.

On 2026-10-25 the user requested launching the latest version after closing the old program. The Release application build succeeded with zero errors and two NU1900 warnings (the package vulnerability information query reported an invalid handle). This does not confirm a successful vulnerability audit. The newly built executable was launched and its main window was observed. Existing global Pause and disabled routing rule settings were preserved. **No automated test run, monitor detail render or live application/VPN forwarding test has been performed for monitor mode.** The earlier 125 passing tests predate this feature and do not validate it.

New unexecuted cases in `ConnectionMonitorTests` cover settings compatibility, routing/capture isolation, proxy configuration versus endpoint evidence, local peer tuples, missing UDP destinations, unknown/scoped routes, path matching, proxy parsing and snapshot limits. New UI smoke cases cover adapter-free monitor mode, toggling back to routing, connection details in English/Russian/Simplified Chinese and clearing details on pause.

After the user requested launching the latest version, the network path evidence extension was built in Release on 2026-10-25: zero errors and two NU1900 warnings about an unavailable vulnerability-information query. The newly built executable was launched and its main window was observed. The loaded configuration showed English, global Pause and one disabled routing rule; no settings were changed during launch. No automated tests, path-detail rendering or forwarding verification were performed. New unexecuted `ConnectionPathAnalyzerTests` and UI cases cover exact versus ambiguous/listener-only ownership, source/route disagreement, proxy management-port isolation, candidate caps, shared proxy attribution, IPv4-mapped IPv6, snapshot-local route caching, mixed paths, evidence detail selection, pause clearing and narrow layouts.

When requested, build and run the solution tests in a separate artifact directory, inspect the monitor screenshots in both themes, then manually observe an application connecting to the configured local proxy. A manual observation should confirm only endpoint evidence and leave the proxy's upstream unknown. Keep routing and VPN settings unchanged for that observation.
